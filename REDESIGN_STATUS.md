## Implemented in this continuation

- Domestic / International creation, Teal default retained, and a labelled search field with native currency selection. International options come exclusively from `GET /api/fx/currencies`, validated against ISO precision metadata. No hardcoded international fallback list or frontend FX vendor request. Registry errors show retry and preserve Domestic IDR creation. An existing international event retains its saved currency when the registry is unavailable.
- Owner types consume `currencyMode`, `baseCurrency`, `currencyLocked`, `fxReferenceRateToIdr`, `fxReferenceDate`, `fxReferenceProvider`; transaction types consume `baseCurrency`, `fxRateToIdr`, `fxRateDate`, `fxRateProvider`, `idrEquivalent`. Legacy responses without currency metadata default to whole-rupiah IDR.
- Event editing is available from both home and active event settings. A fresh owner detail read checks persistent lock state and transaction presence before enabling currency changes. Currency remains locked even when all transactions have been deleted. Server errors, including 409 conflicts, stay visible without dismissing the form or discarding input.
- A currency change explicitly shows the old and new budget/cash allocation and requires acknowledgment that numeric amounts are retained without FX conversion. Unrepresentable precision is rejected. Event edits omit budget writes; the existing audited adjustment flow remains the way to change a budget. New-event currency switches clear the draft amount for re-entry.
- Exact decimal major-unit strings are sent for event budgets, unit prices, cash allocation, reallocations and signed budget adjustments. Accounting uses BigInt minor units for totals, channel balances, budget outcomes and settlement. No money is converted to Number; only a bounded progress percentage crosses that boundary. Full values are formatted without abbreviation, including amounts beyond JavaScript's safe integer range. Safe legacy numeric responses remain accepted.
- Indonesian grouping and comma decimal inputs respect ISO precision (IDR/JPY whole units; SGD/USD two digits; KWD three; other supported ISO currencies use their metadata). API decimals are formatted separately from editable grouped text. Malformed paste is retained for validation. Invalid/overprecision prices and noninteger quantities are rejected before writes.
- Home, active ledger, channel accounting, adjustments/history and completed settlement retain the event currency as primary. Owner and public financial totals show secondary approximate IDR values with `≈`; unavailable references are explicit. Visible reference status includes observation date/provider and identifies older observations without claiming a current rate. Transaction rows use their own immutable snapshot/equivalent, with visible provenance, instead of the current event rate. Evidence controls and private attachment/link upload flow are retained.
- FX Context is absent for IDR. Its native dialog is a mobile bottom sheet and compact desktop inspector, with labelled editable fields in both directions. Conversion uses a single exact decimal event→IDR rate with half-up rounding in the target minor unit. Active tools request only the backend rate endpoint, preserve dated stored references if refresh fails, and identify stale cached responses. With no reference, conversion is disabled while expense recording stays available. Requests are timed out/aborted on close, hidden page or page exit, and stale responses are ignored.
- Completed owner statements display a distinct “Anggaran awal” row only for `initialBudgetKnown === true` and a valid exact snapshot. Unknown/absent legacy snapshots display “Anggaran awal historis tidak tersedia.” Their placeholder is never shown as historical, and neither today's budget nor audited adjustments reconstruct an initial amount. “Anggaran akhir”, expenses, remaining/deficit, channel balances, participant count, per-person shares and undistributed minor-unit remainder remain visible as applicable. Event currency is primary; international totals, including the known initial snapshot, use the frozen event reference only for secondary approximate IDR values.
- Public completed statements use the same known/unknown distinction and explicitly label the current budget “Anggaran akhir”. Both snapshot fields may be absent in old public responses: normalization sets known=false and leaves the initial amount absent, without copying the current budget. If supplied, both fields are required; the flag must be boolean and the amount positive, finite, exact, within the bigint major-unit magnitude bound and representable at the event currency precision, even for an unknown placeholder. Invalid/partial snapshots fail closed. No participant or settlement data is invented for the anonymous projection.
- Public normalization uses explicit backend field allowlists at the root, event, summary and entry levels; unexpected fields, including owner/notes/evidence/participant/reason fields and extra/mismatched currency assertions, now reject the payload. Legacy IDR remains supported. Null/invalid currency, currency mode mismatch, orphan FX metadata, partial transaction FX, inconsistent totals/balances and unsafe monetary transport are rejected. Transaction IDR equivalents continue to be derived from their allowlisted immutable snapshots. Synthetic browser fixtures now model the actual public projection rather than include owner data.
- Completed owner/public converters retain the existing no-refresh guard and show the frozen reference rate/date/provider or an honest unavailable state. A completed public payload becomes Final Statement and stops polling. No fresh FX request or snapshot mutation was added.
- Existing polling safeguards are preserved: six seconds while visible, pause/abort when hidden, immediate resume, stale-response generation checks, no-store, omitted credentials, token header/fragment, redirect rejection, timeout, bounded backoff, last-good-data retention, unchanged-row reuse, revocation hiding/stop, and page-exit cleanup. No owner authentication is imported into the public route.
- Astro route shells and shared eight-mood design are preserved. Existing interactive pages remain Astro/client-side scripts; React/Tailwind and a component-library migration were not introduced in this continuation, consistent with the plan's incremental/no-SPA constraint. Native dialogs remain in use. The companion backend changes are recorded separately in `../backend/LIVE_LEDGER.md`; this frontend continuation did not edit backend code.
- Budget-history lifecycle fix: ordinary owner renders reuse one page-local read per event, including overlapping renders and revisits. Switching events immediately clears old rows; stale event responses and superseded same-event responses cannot update the display. Successful reallocations and adjustments explicitly force a new read for the captured mutation event ID; the following detail refresh reuses that read. A late mutation for another event invalidates only that event's cache. Completed events defer their first history read until the “Tunai & digital” panel is open and retain read-only history. Failed/non-OK reads remain optional and do not retry on ordinary renders; failed forced refreshes retain the last good display. The public route and existing design/currency/evidence behavior remain unchanged.
